# Cloud Management System Using libvirt: Autoscaling Demo



## 1. Overview

This project demonstrates horizontal autoscaling of a CPU-intensive client-server application using the Python `libvirt` API to monitor virtual-machine CPU utilization and manage VM lifecycle operations.

- **server1** (`192.168.122.202`) runs from the beginning.
- **server2** (`192.168.122.21`) is started when load increases and removed when demand falls.
- The autoscaler monitors server1's CPU utilization through libvirt.
- **Scale-out:** when CPU utilization reaches the 60% threshold for the configured consecutive samples, the autoscaler defines server2 from `server2.xml` if necessary, starts it, waits until its HTTP application is ready, and publishes both server URLs in `available_servers.json`.
- **Scale-in:** when load remains low according to the configured scale-in rules, server2 is removed from `available_servers.json`, shut down, and undefined from libvirt.
- The client rereads `available_servers.json` for every request, so it can use the updated server list without restarting.

The demonstration runs four load phases—**low, high, low, high**—to show scale-out, scale-in, and scale-out again.

## 2. Environment

- Ubuntu Linux host with QEMU/KVM and libvirt
- Python 3
- Two Ubuntu Server VMs with one vCPU each
- Host with 12 logical CPUs (as used in the tested setup)

Install the host-side dependencies:

```bash
sudo apt install qemu-kvm libvirt-daemon-system libvirt-clients virt-manager \
    python3-libvirt python3-requests python3-matplotlib
```

## 3. Project files

- `autoscaler.py` — monitors VM CPU utilization, applies scale-out and scale-in rules, starts and stops server2, updates the published server list, and records CPU measurements and lifecycle events.
- `integrated_demo.py` — open-loop client that generates the four load phases and reads `available_servers.json` for each request.
- `plot_results.py` — reads the CSV logs and creates `autoscaling_summary.png` and `summary_stats.csv`. It plots CPU utilization, latency, throughput, and autoscaling/load-phase events, and reports statistics for the load windows.
- `cpu_monitor.py` — prints server1 CPU utilization measured through libvirt for comparison.
- `server1_server.py`, `server2_server.py` — CPU-intensive HTTP server implementations. They are functionally equivalent apart from the server name they report. Install the matching file as `/home/clouduser/server.py` on each VM.
- `cpu-server.service` — systemd unit that starts the server application on boot.
- `available_servers.json` — server URL list used by the client.
- `server1.xml`, `server2.xml` — libvirt domain definitions.
- `cpu_log.csv` — CPU utilization samples.
- `events.csv` — autoscaler and client event log.
- `integrated_demo_results.csv` — per-request results, including latency, success status, phase, and responding server.
- `summary_stats.csv` — summary statistics generated by the plotting script.
- `autoscaling_summary.png` — combined CPU, latency, and throughput plot.
- `benchmark.py`, `load_balancer.py` — earlier closed-loop benchmark utilities; they are not used by the integrated autoscaling demo.
- `results/` — may contain logs and plots from recorded runs.

The scripts locate their files relative to their own folder unless a project directory is supplied through `PROJECT_DIR`.

## 4. Server setup (inside each VM)

Copy the matching server script to `/home/clouduser/server.py` and copy `cpu-server.service` to `/etc/systemd/system/cpu-server.service`. Then run on each VM:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now cpu-server
systemctl is-enabled cpu-server
systemctl is-active cpu-server
```

The server listens on port 8000. Check server1 from the host:

```bash
curl "http://192.168.122.202:8000/?n=100"
```

Confirm that both VMs' network addresses and the paths to their disk images match the domain XML files before running the demo.

## 5. Running the demonstration

Run the commands on the host, from the directory containing the project scripts.

1. Start server1 and verify that its HTTP endpoint responds.
2. Ensure server2 is not running. If it is running, shut it down:

   ```bash
   virsh -c qemu:///system shutdown server2
   ```

3. To demonstrate that the autoscaler can define server2 itself, remove its libvirt definition while keeping its disk files:

   ```bash
   virsh -c qemu:///system undefine server2
   ```

   If server2 is already undefined, no further action is needed.

4. Reset the published list so that only server1 receives requests initially:

   ```bash
   echo '["http://192.168.122.202:8000"]' > available_servers.json
   ```

5. In Terminal 1, start the autoscaler:

   ```bash
   python3 autoscaler.py
   ```

6. In Terminal 2, start the integrated four-phase client:

   ```bash
   python3 integrated_demo.py
   ```

   The run takes approximately **3.5 minutes** and uses the sequence **low load → high load → low load → high load**.

7. After the client prints `CLIENT_ALL_DONE`, allow approximately **40 seconds** for the final scale-in and shutdown to finish. Then press `Ctrl+C` in Terminal 1 if the autoscaler is still running.

8. Generate the plot and statistics:

   ```bash
   python3 plot_results.py
   ```

   This creates `autoscaling_summary.png` and `summary_stats.csv` beside the scripts. To plot logs stored in `results/`, run:

   ```bash
   PROJECT_DIR=results python3 plot_results.py
   ```

### Load and autoscaling settings

The demonstration uses the following configuration:

| Setting | Value |
|---|---:|
| Scale-out CPU threshold | 60% |
| Consecutive high samples for scale-out | 2 |
| Scale-in CPU threshold | 25% |
| Consecutive low samples for scale-in | 5 |
| Minimum low-load duration before scale-in | 20 s |
| Drain period before stopping server2 | 5 s |
| CPU sampling interval | 2 s |
| Low-load request rate | 25 requests/s |
| High-load request rate | 70 requests/s |
| Request size (`n`) | 20000 |
| Client load phases | LOW-1, HIGH-1, LOW-2, HIGH-2 |

The high-load phase is intended to overload a single server. With two servers active, the requests can be shared between them. During a low-load phase, the autoscaler can remove server2 after the scale-in conditions are satisfied.

## 6. Results and plots

Run `plot_results.py` after a demonstration to generate results from the current CSV logs. The plot contains three panels:

1. **CPU utilization:** server1 and server2 CPU usage, the 60% scale-out threshold, the 25% scale-in threshold, and markers for load-phase changes and VM lifecycle events.
2. **Latency:** mean request latency and 95th-percentile (P95) latency in 5-second bins.
3. **Throughput:** completed requests per second for each server and in total, in 5-second bins.

The event markers identify important lifecycle steps, including:

- `OVERLOAD_DETECTED`
- `VM2_DEFINED_FROM_XML` (when server2 is not already defined)
- `VM2_CREATE_CALLED`
- `SERVER2_READY_PUBLISHED`
- `LOW_LOAD_DETECTED`
- `SERVER2_REMOVED_FROM_LIST`
- `SERVER2_SHUTDOWN_CALLED`
- `SERVER2_STOPPED`
- `SERVER2_UNDEFINED`

Use the newly generated `summary_stats.csv` for the measured values of each run. Do not assume that statistics from an earlier single-cycle run describe the current four-phase run.

## 7. CPU measurement: libvirt versus `top` inside the VM

The autoscaler calculates CPU utilization from the change in domain CPU time reported by libvirt (`dom.info()[4]`, in nanoseconds), divided by elapsed wall-clock time and the number of vCPUs.

A comparison with `top` inside the VM may show a small difference at moderate load because libvirt measures host CPU time consumed by the domain process, while `top` reports CPU time accounted for by the guest operating system. At saturation, both measurements should approach 100%, subject to sampling and measurement differences.

For a meaningful comparison, take the `top` measurement inside the VM. Host-level `top` averages usage across the host's logical CPUs and is not directly comparable to a per-VM utilization percentage.

## 8. Limitations and setup notes

- The demo manages one additional replica: server1 is the initial VM and server2 is the scale-out replica. It demonstrates repeated scale-out and scale-in cycles between these two VMs; it is not a general multi-replica scheduler.
- VM disk images are not included and must be provisioned separately.
- VM names, IP addresses, and disk-image paths are specific to this setup. Update `server1.xml` and `server2.xml` if your environment differs.
- `defineXML()` defines the VM using `server2.xml`; it does not create the disk images. The disk image (for example, `server2.qcow2`) and any required seed ISO must already exist at the paths configured in the XML.
- The client depends on the published `available_servers.json` file being readable and updated correctly.
- Results depend on the host's available CPU resources, VM configuration, request rate, and timing. Use the CSV logs generated by the same run when reporting measured results.
